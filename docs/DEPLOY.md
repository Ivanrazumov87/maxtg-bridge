# Развёртывание моста MAX ⇄ Telegram — полная инструкция

Документ рассчитан на то, чтобы по нему мост можно было поднять с нуля без
дополнительных вопросов: и человеку, и ИИ-ассистенту. Кроме шагов установки
здесь собраны **ловушки, на которых проект уже ломался**, — прочитайте раздел
«Чего нельзя менять» до того, как что-то «улучшать» в `max.py`.

## Что получится в итоге

Одна группа MAX и одна обычная группа Telegram работают как единый чат:
сообщение, написанное в одной, появляется в другой с пометкой источника
(`Имя [MAX]: …` в Telegram, `Имя [TG]: …` в MAX). Текст, фото, видео, файлы,
голосовые — в обе стороны (ограничения — в README).

Мост работает от имени **обычного аккаунта MAX** (не бота — у MAX нет открытого
Bot API для групп пользователей) через неофициальный веб-протокол, и от имени
**бота Telegram**.

## Шаг 0. Что нужно заранее

| Что | Зачем |
|---|---|
| Linux-сервер (VPS) с Python **3.10+** | круглосуточная работа. Проверено на Ubuntu 24.04, Python 3.12.3, 2 ГБ RAM — ресурсов хватает с запасом |
| Аккаунт MAX, состоящий в нужной группе MAX | от его имени мост читает и пишет в MAX |
| Бот Telegram | от его имени мост читает и пишет в Telegram |
| Обычная группа Telegram | вторая половина «моста» |

Python ниже 3.10 не подойдёт: в коде используется `match` и аннотации `str | None`.

Гео-ограничений нет: мост проверенно работает с VPS в Германии, прокси не нужен.

## Шаг 1. Бот Telegram

1. В Telegram откройте **@BotFather** → `/newbot` → задайте имя и username → скопируйте **токен**.
2. **Отключите privacy mode**: `/setprivacy` → выберите бота → **Disable**.
   Без этого бот в группе видит только команды, а не обычные сообщения, —
   пересылка TG → MAX молча не будет работать.
3. Добавьте бота в группу Telegram (лучше администратором).
   Если бота добавили в группу ДО отключения privacy — удалите и добавьте заново,
   иначе настройка к этой группе может не примениться.
4. ID группы Telegram: перешлите любое сообщение из группы боту
   [@my_id_bot](https://t.me/my_id_bot). ID начинается с `-100…`.

## Шаг 2. Токен MAX — отдельная сессия для моста

**Главное правило: у моста должен быть СВОЙ токен, которым больше никто не пользуется.**
Если тот же токен одновременно открыт в браузере (web.max.ru), MAX рвёт
соединение, и мост не может залогиниться. Это уже случалось на практике.

Проверенный способ получить отдельный токен:

1. Откройте браузер в режиме **инкогнито** (это отдельное «устройство» для MAX).
2. Зайдите на https://web.max.ru и войдите в аккаунт (по номеру телефона и коду).
3. Нажмите F12 → вкладка **Application** → **Local Storage** → `https://web.max.ru`.
4. Найдите ключ `__oneme_auth_token` — его значение и есть `MAX_TOKEN`.
5. **Закройте окно инкогнито, НЕ нажимая «Выйти»** из аккаунта: выход
   аннулирует сессию, и токен перестанет работать.

Обычный браузер и телефон при этом продолжают работать параллельно — это
другие сессии.

Альтернатива — `python get_token.py` (вход по номеру телефона и коду прямо из
консоли). Скрипт использует метод `MaxClient.auth()` из `max.py`, но в текущей
версии проекта этот путь **не проверялся**; основной способ — инкогнито.

## Шаг 3. ID группы MAX

Откройте https://web.max.ru, зайдите в нужную группу. ID — число в адресной
строке после `web.max.ru/` (для групп отрицательное, например `-7449…`).
Аккаунт, чей токен вы взяли, должен состоять в этой группе.

## Шаг 4. Код на сервер

```bash
apt update && apt install -y python3-venv git
git clone https://github.com/Ivanrazumov87/maxtg-bridge.git /opt/maxtg
cd /opt/maxtg
python3 -m venv venv
venv/bin/pip install -r requirements.txt
```

## Шаг 5. Файл `.env`

**Создавайте `.env` прямо на сервере** (редактором `nano` или через heredoc), а не
копируйте с Windows. Файлы, созданные в Windows, бывают в кодировке UTF-16 —
тогда `python-dotenv` не прочитает переменные, а `pip` не прочитает
`requirements.txt`. Проверка: `file /opt/maxtg/.env` должен показать
`ASCII text` или `UTF-8`, но не `UTF-16`.

```bash
cat > /opt/maxtg/.env <<'EOF'
MAX_TOKEN=токен_из_шага_2
MAX_GROUP_ID=-ID_группы_MAX
TG_BOT_TOKEN=токен_бота
TG_GROUP_ID=-100ID_группы_TG
MONITOR_ID=
EOF
chmod 600 /opt/maxtg/.env
```

`MONITOR_ID` можно не заполнять: он используется только в `starter.py`,
который при запуске через systemd не нужен.

## Шаг 6. Пробный запуск руками

```bash
cd /opt/maxtg && venv/bin/python -u main.py
```

Признак успеха — в консоли:

```
Имя: <имя аккаунта MAX>, Номер: … | ID: …
[bridge] Telegram poller запущен
```

Напишите сообщение в обе группы и убедитесь, что оно дошло до другой стороны.
Остановите процесс (Ctrl+C) — дальше мост будет работать как служба.

При **первом** запуске мост пропускает всё, что накопилось у бота Telegram
раньше, — старые сообщения не выливаются в MAX задним числом.

## Шаг 7. Служба systemd (работа 24/7)

```bash
cp /opt/maxtg/deploy/maxtg.service /etc/systemd/system/maxtg.service
systemctl daemon-reload
systemctl enable --now maxtg
systemctl status maxtg
```

Проверка, что лимит рестартов действительно снят (важно, см. ниже):

```bash
systemctl show maxtg -p StartLimitIntervalUSec   # должно быть 0
```

Если путь установки не `/opt/maxtg` — поправьте `WorkingDirectory` и `ExecStart`
в юните.

Файлы состояния (создаются сами, в git не попадают):
- `bridge_state.json` — позиция чтения Telegram и списки уже пересланных
  `message.id`. Благодаря ему после рестарта ничего не теряется и не дублируется.
  Удалять не нужно; если удалить — мост заново пропустит накопленное в Telegram.

### Нормальное поведение: периодические перезапуски

В логе время от времени появляется:

```
Соединение с MAX потеряно: no close frame received or sent. Перезапуск процесса (systemd)...
```

и сразу за ним снова `Имя: …` / `Telegram poller запущен`. **Это штатно.**
Сервер MAX иногда рвёт соединение; мост в ответ завершает процесс, systemd
поднимает его через 3 секунды, сообщения не теряются. На рабочей установке
(сентябрь 2026) — несколько таких рестартов в сутки.

Тревожный признак другой: рестарты идут **подряд, каждые несколько секунд**,
и строка `Имя: …` не появляется. Это значит, что мост не может залогиниться, —
см. «Диагностика».

## Диагностика

| Симптом | Причина и решение |
|---|---|
| Бесконечные рестарты, логин не проходит | Токен MAX используется ещё где-то (открыт в браузере) или аннулирован (нажали «Выйти»). Получите новый токен по шагу 2, обновите `.env`, `systemctl restart maxtg` |
| В логе `Conflict` / 409 от Telegram | Запущено два экземпляра моста с одним ботом (например, на ноутбуке и на сервере). Оставьте один |
| Из MAX в TG идёт, из TG в MAX — нет | У бота не отключён privacy mode (шаг 1.2) или бот не в группе |
| Логин MAX отвечает `error: internal` / «Something went wrong» | Не токен! См. «Чего нельзя менять», пункт 4 |
| Файл из Telegram не пересылается, отправитель получил предупреждение | Файл больше 20 МБ — ограничение Bot API Telegram, обойти нельзя |

Приём, экономящий время: если мост не встаёт, сначала проверьте токен
отдельно — одноразовым подключением и логином (opcode 19). Если отдельный логин
проходит, а служба всё равно не поднимается, — проблема в процессе/окружении,
а не в токене.

## Чего нельзя менять — ловушки, на которых проект уже ломался

Всё ниже выглядит как странности, которые хочется «исправить». Каждая из них
стоила дней отладки. Если меняете `max.py` — сначала прочитайте.

### 1. Нельзя отвечать на ответы сервера (`cmd` 1 и 3) — `max.py`, `_process_message`

В каждом пакете MAX есть поле `cmd`: `0` — запрос или пуш от сервера,
`1` — ответ на наш запрос, `3` — ошибка. Раньше код это поле не читал: ответ
сервера на наш пинг принимался за пинг сервера, код отвечал на него новым
пингом, сервер отвечал снова — **бесконечная петля**. С каждым циклом
heartbeat добавлялась ещё одна петля; трафик рос до сотен сообщений в секунду,
и примерно через 4 минуты сервер рвал соединение. Внешне это выглядело как
«MAX нестабилен», хотя виноват был сам клиент.

Сейчас в начале `_process_message` стоит проверка: пакеты с `cmd` 1/3 отдаются
тому, кто ждёт ответа, и **больше ничего с ними не делается**. На серверный
пинг (`cmd=0, opcode=1`) отвечаем пакетом `cmd=1` с **тем же** `seq`, а не новым
запросом. Не трогать.

### 2. `ping_interval=None` при подключении — `max.py`, `connect()`

Библиотека `websockets` по умолчанию каждые 20 секунд шлёт свой служебный
ping и рвёт соединение, если не получила ответ. Сервер MAX на такие пинги
не отвечает (у него свой прикладной heartbeat — opcode 1). Без
`ping_interval=None, ping_timeout=None` соединение обрывается само.

### 3. Heartbeat каждые 25 секунд убирать нельзя — `max.py`, `_heartbeat`

Проверено: без трафика от клиента сервер MAX рвёт соединение ровно через
60 секунд. Интервал 25 секунд — с запасом.

### 4. `chatsCount` при логине не больше 100 — `max.py`, `connect()`

Логин (opcode 19) с `chatsCount` 5, 40 и 100 проходит, а с 400 сервер отвечает
`error: internal`. Это легко принять за «протухший токен» и потерять время.
Граница где-то между 100 и 400; стоит 100.

### 5. При обрыве — выход из процесса, а не переподключение — `max.py`, `_listener` / `_exit_for_restart`

Переподключение «на лету» внутри процесса пробовали: оно зависало — фоновые
потоки (heartbeat, обработчики сообщений) мешали новому логину, мост
бесконечно писал «Не смог встать». Поэтому при любом обрыве процесс чисто
завершается (`os._exit(1)`), а systemd поднимает его заново. Отсюда
обязательные настройки юнита: `Restart=always` и `StartLimitIntervalSec=0`
в секции **[Unit]** (в `[Service]` systemd эту строку игнорирует, и через
5 быстрых рестартов служба выключится насовсем).

### 6. Поток чтения — единственный, и он не должен ждать ответов — `max.py`

Сокет MAX читает только один поток (`_listener`). Он же доставляет ответы на
запросы. Если внутри этого потока сделать запрос и ждать ответа (например,
узнать имя пользователя), он будет ждать сам себя — взаимная блокировка
(в логе: «Нет ответа на opcode 32 за 15.0s»). Поэтому обработка входящих
сообщений (opcode 128) вынесена в пул потоков `_worker_pool`.

### 7. Защита от петли пересылки — `main.py`, `bridge.py`, `store.py`

Сообщение, которое мост переслал из TG в MAX, мост сам же видит в MAX как
новое. Чтобы не отправить его обратно, используется три барьера:
(1) сообщение в MAX вида `Имя [TG]: …` (метка `[TG]:` в первых 128 символах,
регулярка `_OWN_FORWARD_RE` в `bridge.py`) обратно не идёт;
(2) каждый `message.id` запоминается в `bridge_state.json` и повторно не
пересылается (переживает рестарт); (3) сообщения ботов в Telegram
игнорируются. Метку `[TG]` в формате пересылки не менять — на ней держится
барьер (1).

## Справка по протоколу MAX (для доработок)

Соединение: `wss://ws-api.oneme.ru/websocket`, заголовок `Origin: https://web.oneme.ru`.
Пакет: `{"ver": 11, "cmd": 0, "seq": N, "opcode": X, "payload": {...}}`,
`seq` — счётчик по модулю 65536.

| opcode | Назначение |
|---|---|
| 1 | heartbeat / ping |
| 6 | приветствие с userAgent (первым пакетом) |
| 17 / 18 | вход по телефону: запрос кода / проверка кода |
| 19 | логин по токену; ответ сразу содержит `profile`, `chats`, `contacts` |
| 32 | информация о контакте (имя) |
| 49 | история чата |
| 64 | отправка сообщения (с вложениями) |
| 67 | редактирование |
| 80 / 87 / 82 | URL для загрузки фото / файла / видео |
| 83 | получить URL видео |
| 128 | пуш: новое сообщение |
| 136 | пуш: загруженный файл обработан |
| 301 | получить URL звука голосового (`{audioId, token}` → ключ `opus`, Ogg/Opus) |

Не решено: отправка в MAX **настоящего** голосового (с плеером и волной).
Сейчас голосовое из TG уходит в MAX файлом `.ogg` — звук воспроизводится.
Перебранные и не сработавшие варианты: attach `_type: AUDIO` с `fileId` от
opcode 87 (сервер: «Invalid attachment»), opcodes 85/86/89/90/303.
Возможные пути: снять загрузку голосового из веб-клиента MAX через DevTools
или использовать официальный Bot API MAX (dev.max.ru), если он применим.

Полезные сторонние реализации протокола: github.com/nsdkinx/vkmax,
github.com/fresh-milkshake/pymax.
